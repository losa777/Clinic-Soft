# კლინიკა — მართვის სისტემა

ავტორიზაცია და როლების გვერდები, პაციენტის რეგისტრაცია, ჯავშნები, ფინანსები (ინვოისები, სალარო, დაზღვევა), ექიმის მოდული (ელექტრონული სამედიცინო ჩანაწერი, დანიშნულებები, ლაბორატორია/ექთანი, დოკუმენტები ხელმოწერით), შეტყობინებები, სტატისტიკა და შიდა ჩატი.

**ტექნოლოგიები:** Next.js 16 (App Router, TypeScript), Auth.js v5 (Credentials, JWT), Prisma 7 + MariaDB/MySQL, Tailwind CSS 4 + shadcn/ui, zod, bcryptjs, Socket.IO (ჩატი).

## მოთხოვნები

- Node.js 20.9+ (ტესტირებულია 24-ზე)
- MariaDB ან MySQL სერვერი და ცარიელი (ან არსებული) ბაზა, მაგ. `clinic`

## ინსტალაცია

```bash
npm install
```

`npm install` ავტომატურად უშვებს `prisma generate`-ს (კლიენტი იქმნება `src/generated/prisma`-ში).

## .env-ის შევსება

დააკოპირეთ `.env.example` → `.env.local` და შეავსეთ:

```env
DB_HOST=10.1.20.242
DB_PORT=3306
DB_USER=...
DB_PASSWORD=...
DB_NAME=clinic
AUTH_SECRET=...
```

`AUTH_SECRET`-ის დასაგენერირებლად:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

> `npx auth secret` ახლა Better Auth-ის CLI-ს უშვებს და სხვა ცვლადს (`BETTER_AUTH_SECRET`) აგენერირებს, ამიტომ გამოიყენეთ ზემოთ მოცემული ბრძანება.

`.env.local` არის `.gitignore`-ში — პაროლები რეპოზიტორიაში არ ხვდება. ბაზის მონაცემები კოდში არსად წერია; მათ კითხულობს `src/lib/db-config.ts`.

## ბაზის მომზადება

```bash
npm run db:setup
```

სკრიპტი (`scripts/setup-db.ts`) იდემპოტენტურია — შეგიძლიათ გაუშვათ რამდენჯერმე:

- ქმნის ყველა ცხრილს (`CREATE TABLE IF NOT EXISTS`, InnoDB, `utf8mb4_unicode_ci`) და ამატებს ახალ სვეტებს/ინდექსებს/შეზღუდვებს არსებულ ცხრილებში (`ensureColumn`, `ensureIndex`, `ensureConstraint` — ეს ცვლის „მიგრაციებს“);
- წერს 8 როლს (`INSERT ... ON DUPLICATE KEY UPDATE`);
- ქმნის სატესტო მომხმარებლებს და ბეჭდავს სიას.

განმეორებით გაშვებისას არსებულ მომხმარებელს პაროლი **არ** ეცვლება (განახლდება მხოლოდ სახელი, გვარი და როლი).

ცხრილის სტრუქტურა აღწერილია `prisma/schema.prisma`-შიც (Prisma კლიენტისთვის). სტრუქტურის შეცვლისას განაახლეთ ორივე ფაილი.

## გაშვება

```bash
npm run dev      # დეველოპმენტი: http://localhost:3000 (tsx server.ts --dev)
npm run build    # production build
npm start        # production სერვერი (build-ის შემდეგ; tsx server.ts)
```

აპლიკაცია ეშვება **`server.ts`-ით** (Next.js-ის custom server): Next და ჩატის Socket.IO ერთ პორტზე. `next dev` / `next start` პირდაპირ **არ** გამოიყენოთ — ჩატი „კავშირი გაწყდა“-ს აჩვენებს (`npm run dev:next` — მხოლოდ realtime-ის გარეშე სამუშაოდ). პორტი/მისამართი: `PORT` (3000), `HOST`. ჩატის realtime კოდის (`src/modules/chat/realtime/`, `server.ts`) შეცვლის შემდეგ სერვერი გადატვირთეთ — HMR მას არ ეხება.

**სხვა მოწყობილობიდან dev რეჟიმში** (ტელეფონი, სხვა კომპიუტერი — `http://10.1.20.245:3000`): Next dev-რესურსებს (`/_next/hmr`) მხოლოდ `localhost`-ს და დაშვებულ მისამართებს აძლევს — სხვაგვარად გვერდი ჩანს, მაგრამ ღილაკები/ჩატი არ მუშაობს. ამ კომპიუტერის ქსელური IP-ები დაშვებულია ავტომატურად (`next.config.ts` → `allowedDevOrigins`); სხვა სახელით შესვლისას (მაგ. `http://clinic-pc:3000`) დაამატეთ `.env.local`-ში `DEV_ALLOWED_ORIGINS=clinic-pc`. `next.config.ts`-ის ან `.env.local`-ის ცვლილების შემდეგ — `npm run dev` გადატვირთეთ.

dev-ის Turbopack ფაილური ქეში გამორთულია (`turbopackFileSystemCacheForDev: false`): Next 16.4.2-ში ფაილის შეცვლის შემდეგ ძველი ქეშით გაშვებისას გვერდი უსასრულოდ ხელახლა იტვირთებოდა. ამიტომ `npm run dev`-ის პირველი გახსნა ~20 წამს იღებს. Next-ის განახლების შემდეგ შეიძლება ხელახლა ჩაირთოს.

> **სქემის ცვლილების შემდეგ** (`prisma/schema.prisma` + `npm run db:setup`) **გადატვირთეთ `npm run dev`** (Ctrl+C → თავიდან): dev სერვერი Prisma კლიენტს მეხსიერებაში ინახავს და ახალ ველებს ვერ ხედავს (შეცდომა „Unknown argument …“ / „Unknown field …“). იგივე — ახალი npm პაკეტის დაყენების შემდეგ.

production-ში (`npm start`) Auth.js მისამართს ენდობა მხოლოდ თუ `.env.local`-შია `AUTH_TRUST_HOST=true` (ან `AUTH_URL=https://<საიტი>`) — სხვაგვარად შესვლა ვერ ხერხდება (`UntrustedHost`).

- **პაციენტები** (`/admin/patients`): პაციენტის მონაცემების და დოკუმენტების რედაქტირება.

- **დაზღვევა** (`/admin/insurance`): სადაზღვევო კომპანიები და პირობები — დაფარვის % და ლიმიტი ერთეულზე, სერვისზე ან მთელ კატეგორიაზე (სერვისის პირობა უპირატესია).
- **რეკვიზიტები** (`/admin/settings`): კლინიკის დასახელება, ს/კ, მისამართი, ტელეფონი, ქვითრის ბოლო ტექსტი (`settings` ცხრილი).
- **ექიმები** (`/admin/doctors`): „ექიმის“ როლის მომხმარებლები. თითოეულს ენიჭება სპეციალობა, ვიზიტის ხანგრძლივობა, კაბინეტი, ჯავშნისთვის ხელმისაწვდომობა და **კვირის სამუშაო განრიგი** (`/admin/doctors/<userId>`). განრიგში თითო დღეს შეიძლება რამდენიმე ინტერვალი ჰქონდეს. ჯავშნის სლოტები ამ განრიგიდან ითვლება. არსებული ჯავშნები განრიგის შეცვლისას არ იცვლება: შენახვის შემდეგ ჩანს, რამდენი მომავალი ჯავშანი აღარ ემთხვევა ახალ განრიგს. ახალი ექიმი ჯერ „მომხმარებლებში“ ემატება `doctor` როლით.
- **სპეციალობები** (`/admin/specialties`): დამატება, გადარქმევა, წაშლა. წაიშლება მხოლოდ ის სპეციალობა, რომელიც არცერთ ექიმს არ აქვს მინიჭებული.
  - **მაჩვენებლები** (`/admin/specialties/<id>`, სპეციალობის სახელზე დაჭერით): სპეციალობის ვიზიტის ფორმის მაჩვენებლები — **რაოდენობა შეუზღუდავია**. ახალი მაჩვენებელი: დასახელება, ტიპი (რიცხვი / ტექსტი / არჩევანი სიიდან / კი-არა), მხარე (ერთი / OD-OS / მარჯვ.-მარცხ.), ერთეული, დასაშვები ფარგლები, ნორმა (გადაცდენისას ექიმი ↑/↓ ხედავს), ათწილადები. არსებული — „კატალოგიდან დამატება“ (ერთი მაჩვენებელი რამდენიმე სპეციალობას შეიძლება ჰქონდეს). რიგი, „სავალდებულო“ (ვიზიტი მის გარეშე არ დასრულდება), სპეციალობიდან მოხსნა (ძველ ვიზიტებში მნიშვნელობები რჩება). ასევე — საერთო ვიტალური (წნევა, პულსი...) ჩანდეს თუ არა. ნიმუშები: ოფთალმოლოგია (Vis, თვალშიდა წნევა, Sph/Cyl/Ax — OD/OS) და კარდიოლოგია. ცხრილები: `measurement_definitions`, `specialty_measurements`, `encounter_measurements`; ვიზიტზე იწერება სპეციალობა (`encounters.specialty_id`). მაჩვენებლები ჩანს ისტორიაში და ავტომატურად ივსება დოკუმენტებში (ფორმა 100 — პ. 12).

**წესები:**

- ადმინისტრატორი საკუთარ ანგარიშს ვერ წაშლის, ვერ გათიშავს და საკუთარ თავს ადმინის როლს ვერ ჩამოართმევს.
- სისტემაში ერთი აქტიური ადმინისტრატორი მაინც უნდა დარჩეს.
- 8 სისტემური როლი (`src/lib/roles.ts`) არ იშლება, მათი სახელის შეცვლა კი შეიძლება.
- როლი, რომელსაც მომხმარებლები ჰყავს, არ იშლება.
- როლის კოდი შექმნის შემდეგ არ იცვლება, რადგან ის გვერდის მისამართია (`/surgeon`). დამატებითი როლის მომხმარებელი შესვლისას საერთო როლის გვერდს ხედავს.
- გათიშვა, წაშლა და როლის ან სახელის შეცვლა **მაშინვე** მოქმედებს: სესია ყოველ მოთხოვნაზე მოწმდება ბაზაში.
- წაშლა შეუქცევადია. თუ წვდომა მხოლოდ დროებით უნდა შეიზღუდოს, გამოიყენეთ „გათიშვა“.

ყველა Server Action სერვერზე თავიდან ამოწმებს, რომ მომხმარებელი ადმინისტრატორია (`requireRole("admin")`).

- **რეგისტრატორი**:
  - `/registrar`: ძებნა სახელით და გვარით (ნებისმიერი რიგით, ქართულად ან ლათინურად) ან პირადი ნომრით (სრულით ან მინიმუმ 4 პირველი ციფრით). შედეგში ჩანს სახელი, გვარი, ტელეფონი, პირადი ნომერი და დაბადების თარიღი; ერთდროულად მაქსიმუმ 20 შედეგი. ძებნა მუშაობს ინდექსებით, სიტყვის დასაწყისით.
  - `/registrar/patients/<id>`: პაციენტის სრული ინფორმაცია მხოლოდ სანახავად, დოკუმენტების დამატება შეიძლება.
  - `/registrar/new`: ახალი პაციენტის რეგისტრაცია. ძებნიდან გადმოსვლისას პირადი ნომერი ან სახელი/გვარი უკვე შევსებულია. შენახვის შემდეგ იხსნება პაციენტის გვერდი.

  - რეგისტრაციისას (აქ და ჯავშნისას სწრაფ ფორმაში) შეიძლება მიეთითოს **დაზღვევა** — „პაციენტი დაზღვეულია“: კომპანია, პოლისის ნომერი, ვადა. არასავალდებულოა; პაციენტი და პოლისი ერთ ტრანზაქციაში ინახება (უფლება: `invoices.create` ან `insurance.manage`).
  - პაციენტის ბარათს აქვს ჩანართები: **„ინვოისები“** (ჯამური ვალი, ინვოისების სია, „ახალი ინვოისი“) და **„დაზღვევა“** (პოლისები: დამატება, გათიშვა). ძებნის შედეგებში ვალიანი პაციენტი „ვალი: …“ ნიშნით ჩანს. ინვოისები და გადახდები: იხ. „ფინანსები“.
- **ადმინისტრატორს** `/admin/patients`-ში აქვს ძებნა, პაციენტის ბარათი მონაცემების რედაქტირებით, ინვოისების სია (სანახავად) და პოლისები. ახალი პაციენტის რეგისტრაცია მხოლოდ რეგისტრატორს აქვს (სერვერზეც მოწმდება).

  არსებული პაციენტის მონაცემებს რეგისტრატორი ვერ ცვლის.
- **ადმინისტრატორი** (`/admin/patients`): იგივე ფორმა, დამატებით არსებული პაციენტის რედაქტირება და დოკუმენტის წაშლა.

ძებნა იწყება 11-ე ციფრის შეყვანისას ან ველიდან გასვლისას (`patients.personal_id`-ის UNIQUE ინდექსით). ნომრის შეცვლისას ნაპოვნი პაციენტის მონაცემები ფორმიდან იშლება. First Name / Last Name ავტომატურად ივსება ქართულიდან (`src/lib/transliterate.ts`), სანამ ხელით არ შეცვლით.

**დოკუმენტები** ინახება დისკზე: ნაგულისხმევად პროექტის `storage/documents` საქაღალდეში (git-ში არ შედის), ან `.env.local`-ის `DOCUMENTS_DIR`-ში (მაგ. სხვა დისკზე). საქაღალდე `public/`-ის გარეთაა (ბრაუზერიდან პირდაპირ არ იხსნება), და მისი სარეზერვო ასლი უნდა კეთდებოდეს ბაზასთან ერთად. ბაზაში (`patient_documents`) მხოლოდ მეტამონაცემებია. ფაილი იკითხება მხოლოდ `/api/patient-documents/<id>`-ით, სესიისა და როლის შემოწმების შემდეგ. დასაშვებია JPG, PNG და PDF; ტიპი მოწმდება ფაილის შიგთავსით. ლიმიტია 10 MB ფაილზე და 10 ფაილი / 40 MB ერთ შენახვაზე. დასკანერებული ფაილები შენახვამდე ბრაუზერშია; შენახვისას ჯერ იწერება დისკზე, მერე პაციენტი და დოკუმენტები ერთ ტრანზაქციაში. ჩავარდნისას ჩაწერილი ფაილები იშლება.

ტესტები: იხ. „ტესტები“.

## ექიმთან ვიზიტის დაჯავშნა

ცხრილები: `specialties`, `doctors` (`users`-ის პროფილი: სპეციალობა, ვიზიტის ხანგრძლივობა, კაბინეტი, აქტიურობა), `doctor_schedules` (კვირის დღე 1–7, დრო თბილისის დროით; დღეში რამდენიმე ინტერვალი შეიძლება), `appointments`. იქმნება `npm run db:setup`-ით. სპეციალობებს, ექიმებსა და განრიგს მართავს ადმინისტრატორი (`/admin/specialties`, `/admin/doctors`). ჯავშნებში ჩანს მხოლოდ ექიმი, რომელიც ხელმისაწვდომადაა მონიშნული, მომხმარებელი აქტიურია და აქვს `doctor` როლი. სატესტო მონაცემები (5 სპეციალობა, 6 ექიმი გრაფიკით, 20 პაციენტი, პირადი ნომრები `01099000001`–`01099000020`) ემატება ბრძანებით:

```bash
npm run db:seed
```

- `/registrar/booking`: **ვიზიტის დაჯავშნა**. ჯერ ირჩევა პაციენტი: ძებნა პირადი ნომრით, სახელით/გვარით ან ტელეფონით, მაქსიმუმ 20 შედეგი. თუ პაციენტი ვერ მოიძებნა, მისი რეგისტრაცია იქვე შეიძლება. შემდეგ ირჩევა სპეციალობა, ექიმი, თარიღი და თავისუფალი სლოტი, ბოლოს ემატება კომენტარი. სლოტები ითვლება ექიმის გრაფიკიდან და ვიზიტის ხანგრძლივობიდან. დაკავებული და გასული სლოტები ჩანს, მაგრამ გათიშულია. ყვითლადაა მონიშნული სლოტი, რომელზეც პაციენტს სხვა ექიმთან უკვე აქვს ჯავშანი.
- `/registrar/appointments`: **დღის ჯავშნები**, თარიღისა და ექიმის ფილტრით, 25 ჩანაწერი გვერდზე. აქ შეიძლება სტატუსის შეცვლა (დაჯავშნილი → მობრძანდა → დასრულებული, ან არ გამოცხადდა), ჯავშნის გადატანა იმავე ექიმთან სხვა დროზე და გაუქმება მიზეზის მითითებით.

**წესები:**

- ერთ ექიმს ერთ დროს ორი ჯავშანი არ ექნება, პაციენტს კი ერთ დროს ორ ექიმთან ჯავშანი არ ექნება. ამას სერვერი ამოწმებს ტრანზაქციაში: ჯერ `SELECT ... FOR UPDATE`-ით იკეტება ექიმისა და პაციენტის ჩანაწერი, შემდეგ მოწმდება დროის გადაფარვა (READ COMMITTED) და მხოლოდ ამის შემდეგ იწერება ჯავშანი. ასე ორი რეგისტრატორი ერთდროულად ერთსა და იმავე სლოტს ვერ დაჯავშნის. არჩეული დრო სერვერზე თავიდან მოწმდება ექიმის გრაფიკით.

- ჯავშნის შექმნა — უფლება `appointments.book` (რეგისტრატორი, ექიმი), სტატუსი/გადატანა/გაუქმება — `appointments.manage` (რეგისტრატორი). ეს ყველა Server Action-ში სერვერზე მოწმდება.

## ფინანსები (`src/modules/finance/`)

ძველი „პაციენტის მიღება“ (`visits`, `visit_services`, `visit_payments`) ჩაანაცვლა ინვოისებმა: `db:setup` ძველ ვიზიტებს ერთხელ გადაიტანს ინვოისებში (`legacy_visit_id`), ძველი ცხრილები არქივად რჩება.

**რეგისტრატურა:** ჩანართები „ინვოისები“, „სალარო“, „დავალიანებები“, „ანგარიშები“. **ადმინი:** „ფინანსები“ (`/admin/invoices`, `/admin/cash`, `/admin/debts`, `/admin/reports`) — იგივე ეკრანები, ყველა მოქმედებით (მათ შორის დაბრუნება). **ბუღალტერი/დირექტორი** (`/accountant`, `/director`): დღის ანგარიში, ინვოისები და დავალიანებები — მხოლოდ სანახავად.

- **ინვოისი** (`INV-2026-000001`, წლის მიხედვით თანმიმდევრული): იქმნება პაციენტის ბარათიდან, ძებნის შედეგიდან ან ჯავშნიდან („ჯავშნები“ → „ინვოისი“ — ექიმი და ექიმის **კონსულტაციის სერვისი** ჩაჯდება ავტომატურად; კონსულტაციის სერვისი ექიმს ენიჭება „ადმინი → ექიმები“). სერვისები ძებნით, რაოდენობა, ფასდაკლება %. ერთ ჯავშანზე ერთი ინვოისი.
- **დაზღვევა**: პაციენტის მოქმედი პოლისით (აქტიური, თარიღებში, კომპანია აქტიური) ყოველ ხაზზე ითვლება დაზღვევის წილი = (ფასი × რაოდ. − ფასდაკლება) × % , მაგრამ არა მეტი ლიმიტი × რაოდ.; დანარჩენი — პაციენტის თანაგადახდა. დაზღვევა კონკრეტულ ინვოისზე შეიძლება გამოირთოს მიზეზით.
- **გადახდა**: ნაღდი (მხოლოდ ღია ცვლით; მიღებული თანხა → ხურდა) ან ბარათი (ტრანზაქციის ნომერი / ბოლო 4 ციფრი — სრული ნომერი არ მიიღება). შეიძლება ნაწილობრივი და რამდენიმე გადახდა; ზედმეტი გადახდა არ მიიღება. **დაბრუნება** (`payments.refund`) — ახალი ჩანაწერი მიზეზით. **გაუქმება** — მიზეზით, მხოლოდ თუ გადახდილი თანხა არ არის (ჯერ დაბრუნება).
- **ქვითარი** ყოველ გადახდასა და დაბრუნებაზე (`RCP-2026-000001`): 80 მმ თერმო ან A4, რეკვიზიტებით; ყოველი ბეჭდვა აღირიცხება, პირველის შემდეგ — „დუბლიკატი“.
- **დავალიანება** = გადაუხდელი პაციენტის წილი ღია ინვოისებზე — ყოველთვის ითვლება მოთხოვნით (ცალკე ველი არ არის). სია ფილტრით (ინვოისის თარიღი, მინ. თანხა), გვერდებით, CSV ექსპორტით (Excel ხსნის); სადაზღვევო დავალიანება კომპანიების მიხედვით პერიოდში.
- **სალარო**: ცვლის გახსნა საწყისი ნაღდით (ერთ მომხმარებელს ერთი ღია ცვლა — ბაზის UNIQUE); დახურვისას მოსალოდნელი = საწყისი + ნაღდი გადახდები − ნაღდი დაბრუნებები, ფაქტობრივი შეყავს მოლარეს, სხვაობა ინახება (სხვაობისას განმარტება სავალდებულოა).
- **დღის ანგარიში** (თარიღი, მოლარე): ნაღდი, ბარათი, დაბრუნებები, ინვოისები და დაზღვევის წილი, სერვისების მიხედვით, გაუქმებული ინვოისები და დაბრუნებები; ბეჭდვა და CSV.
- **ფინანსური ანალიზი** (`reports.finance` — დირექტორი, ბუღალტერი, ადმინი; `/<როლი>/analytics`): პერიოდი (სწრაფი არჩევანი: ეს თვე, წინა თვე, ბოლო 30 დღე / 3 თვე, ეს წელი), შედარება იმავე ხანგრძლივობის წინა პერიოდთან (%). მაჩვენებლები: დარიცხული, მიღებული (წმინდა), საშუალო ინვოისი, პაციენტები, დაზღვევის წილი, ფასდაკლება, დაბრუნებები, მასალის ხარჯი საწყობიდან (`inventory.reports`-ით). დინამიკის გრაფიკი (62 დღემდე — დღეებით, მეტი — თვეებით; ცხრილის სახითაც), ექიმების, სერვისების კატეგორიების, სერვისების (top 15) და სადაზღვევოების ჭრილი; ბეჭდვა, ექიმების და სერვისების CSV. დარიცხული — ინვოისის თარიღით (როგორც დღის ანგარიშში), მიღებული — გადახდის თარიღით (`src/modules/finance/server/analytics.ts`).

**წესები:** თანხები DECIMAL(12,2), გამოთვლა სერვერზე მთელ თეთრებში (`src/modules/finance/calc.ts`, ტესტები — `calc.test.mts`). გადახდა, დაბრუნება, ქვითარი არ იცვლება და არ იშლება. ყველა ოპერაციაში ინახება ვინ და როდის. მრავალნაბიჯიანი ოპერაციები ერთ ტრანზაქციაშია: ინვოისი/ცვლა იკეტება (`SELECT … FOR UPDATE`), ამიტომ ერთდროული გადახდები ზედმეტს ვერ ჩაწერს. ანგარიშები და ვალი SQL-ში აგრეგაციით ითვლება.

**სტრუქტურა:** `calc.ts` (სუფთა გამოთვლები), `schema.ts` (zod), `server/` (ფასი/დაზღვევა, ინვოისები, გადახდები, სალარო, ვალი, ანგარიშები), `actions/` (Server Actions, `requirePermission`), `components/` (InvoiceForm, PaymentForm, ReceiptPrint, DebtList, CashShiftPanel, DailyReport…), `screens/` (როლზე დამოუკიდებელი გვერდები), `routes.ts` (მისამართები როლების მიხედვით — ახალი როლისთვის ჩანაწერი აქ და გვერდები, ნიმუშია `accountant/`).

**სატესტო მონაცემები** (`npm run db:seed`, `scripts/seed-finance.ts`): 18 სერვისი 4 კატეგორიით, 3 (გამოგონილი) სადაზღვევო კომპანია პირობებით, 5 პოლისი, 7 ინვოისი სხვადასხვა მდგომარეობით (გადახდილი, ნაწილობრივ, გადაუხდელი, დაბრუნებით, გაუქმებული).

### ექიმის გვერდი (`/doctor`)

- **დღის განრიგი:** მარცხნივ საკუთარი ვიზიტები (დღე/კვირა, სტატუსის ფილტრი), ზემოთ — მომლოდინეები მოსვლის რიგით (ცოცხალი რიგიც), პირველადი/განმეორებითი ნიშნით. მარჯვნივ — არჩეული პაციენტის ბარათი.
- **პაციენტის ბარათი:** ალერგიები წითლად ზემოთ, სამედიცინო პროფილი, ჩანართები **ვიზიტი, ისტორია, კვლევები, დანიშნულებები, დოკუმენტები**. ბარათის ყოველი ნახვა აუდიტში იწერება. „პაციენტები“ — ძებნა (პირადი ნომერი, სახელი, ტელეფონი) და ბარათი ვიზიტის გარეშე (სანახავად).
- **ვიზიტი:** „მიღების დაწყება“ → ფორმა ავტოშენახვით (2.5 წმ), ვიტალური ნორმიდან გადახრის ნიშნით და BMI-ით, ICD-10 ძებნით, შაბლონებით. ჩანაწერი ორ ფანჯარაში თუ ღიაა, ძველი ვერსია ახალს არ გადაეწერება. **ექიმი ასწორებს მხოლოდ საკუთარ ვიზიტს** — სხვისი მხოლოდ სანახავადაა.
- **დანიშნულებები:** რეცეპტი (პაციენტის ალერგიას თუ ემთხვევა — გაფრთხილება, დადასტურება აუდიტში იწერება; ბეჭდვა A4), ლაბორატორიული/ინსტრუმენტული კვლევები → ლაბორანტის რიგი, პროცედურები → ექთნის რიგი; გაუქმება — სანამ შესრულება დაიწყება. **განმეორებითი ვიზიტი** და **მიმართვა სპეციალისტთან** — ჯავშნის მოდულით (`/doctor/booking`, პაციენტი წინასწარ არჩეულია).
- **ვიზიტის დასრულება:** ფორმა ინახება → მოწმდება ძირითადი დიაგნოზი → ერთ ტრანზაქციაში: ინვოისი (ფასები ფასების ცხრილიდან — **ექიმი ფასს ვერ ცვლის**, დაზღვევა ავტომატურად), დანიშნულებები დარიცხულად (ორჯერ არ ირიცხება), ჩანაწერი იკეტება, ჯავშანი „დასრულებული“. ჯავშანს ინვოისი თუ ჯერ არ აქვს — ინვოისში ჩაჯდება კონსულტაცია + კვლევები/პროცედურები; თუ რეგისტრატურამ უკვე შექმნა — **დამატებითი ინვოისი** მხოლოდ დანიშნულებებით. გადახდა — რეგისტრატურაში.
- **სტატისტიკა** (`/doctor/stats`): ვიზიტები, პაციენტები (პირველადი/განმეორებითი), საშუალო ხანგრძლივობა, არ გამოცხადდა, დასრულებული ვიზიტები დღეების მიხედვით, ხშირი დიაგნოზები, დანიშნულებები და დოკუმენტები, ინვოისები — პერიოდის ფილტრით.

**ლაბორანტი** (`/lab`): კვლევების რიგი (ძველი პირველი) → „ნიმუში აღებულია“ → შედეგი ტექსტით და/ან ფაილით (JPG/PNG/PDF; ინახება პაციენტის ფაილებში) → „მზადაა“. **ექთანი** (`/nurse`): პროცედურების რიგი → „შესრულდა“ შენიშვნით. ორივე შემთხვევაში ექიმი შეტყობინებას იღებს, შედეგი ბარათში ჩანს. სიები — 30 ჩანაწერი გვერდზე.

- „წინასწარი ნახვა (PDF)“ — „დრაფტი“ წყალნიშნით (`/api/medical-documents/<id>/preview`). „ხელმოწერა“ → PDF ხელმოწერებით ინახება პაციენტის ფაილებში, ფიქსირდება `sha256`, დოკუმენტი **იკეტება** (აღარ იცვლება და არ იშლება — მათ შორის პაციენტის ფაილებიდან). შესწორება — „ახალი ვერსია“ (წინა → „ჩანაცვლებული“). „შემოწმება“ ადარებს შენახული PDF-ის sha256-ს.
- PDF: `pdf-lib` + ფონტები Noto Sans/Serif Georgian (`@fontsource/*`, OFL) — `src/modules/emr/documents/` (`typeset.ts`, `pdf.ts`).
- **ფორმა IV-100/ა** (`form100-pdf.ts`) — ოფიციალური ნიმუშის განლაგებით: 20 პუნქტი, დიაგნოზი „ძირითადი / გართულება / თანმხლები“ (ვიზიტის ფორმაში დიაგნოზის ტიპი), კვლევები და პროცედურები კოდითა და თარიღით, მედიკამენტების ცხრილი (რაოდენობა, რეცეპტის ნომერი — რეცეპტიდან), ექიმისა და **ხელმძღვანელის** ხელმოწერა, **ბეჭედი**, გაცემის თარიღი. **ცნობის №** ენიჭება ხელმოწერისას (თანმიმდევრული), **სამედიცინო ბარათის №** (`6914/2026`) — მიღების დაწყებისას, წლის მიხედვით.
- **ხელმოწერის რეჟიმი** ყოველ ხელმომწერზე: „ელექტრონულად“ (პადით) ან „დაბეჭდვის შემდეგ“ (PDF-ში ცარიელი ადგილი, ხელი ეწერება დაბეჭდილზე).
- **ადმინი → რეკვიზიტები:** დაწესებულების ხელმძღვანელის სახელი (პ. 19), ბეჭდის სურათი (PNG გამჭვირვალე ფონით / JPG, ≤ 1 MB, ინახება `DOCUMENTS_DIR`-ში), ნუმერაციის გაგრძელება (ბოლო გაცემული ცნობის № და მიმდინარე წლის ბოლო ბარათის №).
- **ფორმის შეცვლა** (მაგ. ოფიციალური IV-100/ა ნიმუშით): `src/modules/emr/documents/templates.ts` → შაბლონის `fields` (ველის დამატება/წაშლა/გადარქმევა — ფორმაში და PDF-ში ავტომატურად აისახება), `prefill` — რით ივსება ვიზიტიდან, `signers` — ვინ აწერს ხელს. ახალი დოკუმენტის ტიპისთვის დაამატეთ შაბლონი და მნიშვნელობა `medical_documents.type` ENUM-ში (`setup-db.ts` + `schema.prisma`).

## შიდა ჩატი (`src/modules/chat/`)

ყველა შესული თანამშრომლისთვის (ყველა როლი): სრული გვერდი **`/chat`** (ზედა პანელის 💬 ღილაკი, წაუკითხავების რაოდენობით) და **popup** ეკრანის მარჯვენა ქვედა კუთხეში ყველა გვერდზე (`/chat`-ის გარდა). ორივე ერთსა და იმავე კომპონენტებს და state-ს იყენებს; ერთ ტაბზე — ერთი Socket.IO კავშირი (`ChatProvider`, dashboard layout-ში — გვერდებს შორის არ წყდება).

- **საუბრები:** პირადი (ორ ადამიანს შორის ერთი — `direct_key` UNIQUE) და ჯგუფური (სახელი, მონაწილეებს მართავს შემქმნელი; გასვლა — ყველას; შემქმნელის გასვლისას ჯგუფი ყველაზე ძველ მონაწილეს გადაეცემა). ჩამაგრება, ხმის გამორთვა. **საუბრის წაშლა** (⋮ → „საუბრის წაშლა“) — მხოლოდ თქვენთვის: სიიდან და ისტორიიდან ქრება (`conversation_members.cleared_message_id`), სხვებს მიმოწერა რჩება, ბაზაში არაფერი იშლება; ახალ შეტყობინებაზე საუბარი ისევ ჩნდება, ძველი ისტორიის გარეშე.
- **თანამშრომლების ძებნა** სახელით/გვარით/როლით (debounce), **Favorites** სტატუსებით. გათიშული თანამშრომელი ძებნაში არ ჩანს, ჩატზე წვდომა არ აქვს, მისი ძველი შეტყობინებები რჩება.
- **სტატუსები:** 🟢 აქტიური (ბოლო 5 წთ-ში აქტივობა ნებისმიერ ტაბში), 🟡 არ არის კომპიუტერთან, ⚪ გასულია (+ „ბოლოს იყო“; ყველა ტაბის დახურვიდან 5 წმ-ში, გასვლისას — მაშინვე), 🔴 „არ შემაწუხოთ“ (ხელით; ხმისა და შეტყობინებების გარეშე). ზღვარი — `CHAT_AWAY_MINUTES` (.env.local).
- **შეტყობინებები:** Enter — გაგზავნა, Shift+Enter — ახალი ხაზი; ბმულები; რედაქტირება/წაშლა (ძველი ტექსტი — `message_revisions`, ფიზიკურად არაფერი იშლება); პასუხი (quote); ✓/✓✓ (ჯგუფში — ვინ წაიკითხა); „წერს…“; ძებნა საუბარში; ისტორია ნაწილ-ნაწილ (cursor — id); optimistic გაგზავნა „ხელახლა ცდით“; emoji.
- **ფაილები:** ღილაკით, ჩასმით (paste), გადმოტანით; ≤ 10 MB, 4 ფაილი შეტყობინებაში, JPG/PNG/GIF/WEBP/PDF/DOCX/XLSX/TXT (`src/modules/chat/config.ts`). ტიპი მოწმდება შიგთავსით. ინახება `DOCUMENTS_DIR/chat/`-ში, გაიცემა მხოლოდ საუბრის მონაწილეს (`/api/chat/attachments/<id>`).
- **შეტყობინება მომხმარებელს:** ხმა, ტაბის სათაურში `(3) …`, toast, ბრაუზერის Notification (ტაბი ფონზეა; ნებართვით). ხმაგამორთულ საუბარში და „არ შემაწუხოთ“-ზე — მხოლოდ რაოდენობა. პარამეტრები (⚙ საუბრების სიაში) ინახება ბაზაში.
- **ისტორიის გასუფთავება** („ადმინი → ჩატი“): მთლიანი მიმოწერის წაშლა, ან ავტომატური — „ინახება ბოლო N დღე“ (დღეში ერთხელ, `src/instrumentation.ts`). შეტყობინებები, ისტორია და ფაილები (დისკიდანაც) ფიზიკურად იშლება; საუბრები და ჯგუფები რჩება (`src/modules/chat/server/retention.ts`).

| ცხრილი | შინაარსი |
| --- | --- |
| `conversations` | საუბარი: `type` direct/group, `direct_key` (UNIQUE), `last_message_id/at` (სია ერთი მოთხოვნით) |
| `conversation_members` | მონაწილე: `role` owner/member, `last_read_message_id` (წაუკითხავები და ✓✓ — ცალკე ჩანაწერების გარეშე), `muted`, `pinned` |

| `user_favorites`, `user_presence`, `user_chat_settings` | Favorites; „არ შემაწუხოთ“ და ბოლო აქტივობა (მიმდინარე სტატუსი — სერვერის მეხსიერებაში); ხმა/notification |

**Realtime:** Socket.IO (`/api/chat/socket`) იმავე http სერვერზე (`server.ts`). ავტორიზაცია — Auth.js-ის cookie (JWT) + `is_active` ბაზაში; სხვა საიტიდან (Origin) კავშირი უარყოფილია; სესიის ვადის, გასვლის, გათიშვისას კავშირი წყდება. სოკეტით მხოლოდ მიწოდება ხდება — მოქმედებები REST-ით (`src/app/api/chat/`, zod, rate limit). ხელახლა დაკავშირებისას ბრაუზერი გამოტოვებულს სერვერიდან იღებს.

**Deploy:** ერთი Node პროცესი (`npm start`). reverse proxy-ის (IIS / nginx) უკან ჩართეთ WebSocket upgrade `/api/chat/socket`-ზე (თუ არა — Socket.IO long-polling-ზე გადადის, უფრო ნელა). რამდენიმე instance-ზე საჭირო იქნება Socket.IO Redis adapter (სტატუსები და rate limit ახლა ერთი პროცესის მეხსიერებაშია). `output: "standalone"` custom server-თან არ მუშაობს.

**სტრუქტურა:** `config.ts`, `types.ts`, `schema.ts`, `format.ts`, `linkify.ts`, `time.ts`, `files.ts`, `presence.ts` (სუფთა, ტესტებით); `server/` (წვდომა — `access.ts`, საუბრები, შეტყობინებები, ფაილები, ძებნა, პარამეტრები); `realtime/` (Socket.IO, ავტორიზაცია, სტატუსები); `client/` (store, `ChatClient`, provider, აქტივობა, ხმა/notification); `components/`; `screens/` (გვერდი, popup, შეტყობინებები).

## უსაფრთხოება: HTTPS, შესვლის დაცვა, პაროლები

### HTTPS კლინიკის ქსელში

სერვერზე (ერთხელ): `npm run https:setup` — იქმნება კლინიკის საკუთარი „სანდო ცენტრი“ (CA) და სერვერის სერტიფიკატი ამ კომპიუტერის სახელზე და ყველა IP-ზე (დამატებით: `npm run https:setup -- --name clinic-pc --ip 10.1.20.245`). საჭიროა OpenSSL (Git for Windows-ს მოყვება). ფაილები — `certs/` (git-ში არ შედის).

1. `.env.local`: `HTTPS_KEY_FILE=certs/server.key`, `HTTPS_CERT_FILE=certs/server.crt`, `AUTH_TRUST_HOST=true`; სურვილისამებრ `HTTP_REDIRECT_PORT=80` (http:// → https://). გადატვირთეთ სერვერი — `https://<სერვერი>:3000`.
2. კლინიკის ყველა კომპიუტერზე (ერთხელ): `certs/clinic-ca.crt` და `certs/install-clinic-ca.cmd` ერთ საქაღალდეში → `install-clinic-ca.cmd` (ადმინისტრატორის უფლებას თავად ითხოვს). Edge/Chrome/Firefox Windows-ის სანდო ცენტრებს ენდობიან — გაფრთხილება აღარ ჩანს. **`clinic-ca.key` სერვერიდან არ გაიტანოთ** (მისით ნებისმიერ საიტზე „სანდო“ სერტიფიკატის შექმნა შეიძლება).
3. სკანერის აგენტი: `config.json`-ის `allowedOrigins`-ში დაამატეთ ახალი `https://` მისამართი.

განმეორებით გაშვება (ახალი IP, სერტიფიკატის ვადა — ~2 წელი): CA იგივე რჩება, კომპიუტერებზე ხელახლა დაყენება არ სჭირდება. https-ზე სერვერი აგზავნის HSTS-ს; ყველა პასუხზე — `X-Content-Type-Options`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy` (`next.config.ts`). Auth.js-ის cookie https-ზე `__Secure-` პრეფიქსით იწერება. Node კლინიკის CA-ს ენდობა (`server.ts` — Next-ის შიდა მოთხოვნებისთვის).

### შესვლის დაცვა (`src/lib/login-lock.ts`, `login-guard.ts`)

- **5 წარუმატებელი ცდა 15 წუთში** ერთ მომხმარებელზე → შესვლა 15 წუთით იბლოკება (სწორი პაროლითაც); **20 ცდა 15 წუთში ერთი IP-დან** (სხვადასხვა სახელით) → IP იბლოკება. შესვლის ფორმა დარჩენილ წუთებს აჩვენებს.
- ადმინი: „მომხმარებლები“ — ნიშანი „დაბლოკილია HH:MM-მდე“ და მოქმედება „განბლოკვა“.
- არარსებული მომხმარებლის სახელზეც პაროლის შედარება ხდება — პასუხის დრო არ ამხელს, არსებობს თუ არა სახელი.
- ყველა ცდა — `login_attempts` (90 დღე) და აუდიტში (`login`, `login_failed`, `login_blocked`). შემოწმება ხდება `auth.ts`-ის authorize-ში — ფორმის გვერდის ავლითაც.

### პაროლი

- **ყველა თანამშრომელი:** ზედა პანელის 🔑 → `/account/password` (ამჟამინდელი პაროლი, ახალი ორჯერ). წესი: მინიმუმ 8 სიმბოლო, ასო და ციფრი, არ შეიცავს მომხმარებლის სახელს (`src/lib/password-policy.ts` — იგივე ადმინის ფორმაშიც). ამჟამინდელი პაროლის არასწორი შეყვანა წარუმატებელ ცდად ითვლება.
- შეცვლისას (თანამშრომელი ან ადმინი) `users.session_version` იზრდება: **ყველა ღია სესია ყველა კომპიუტერზე და ჩატის კავშირი წყდება** — შესვლა ახალი პაროლით.

## სკანერი (სარეგისტრატურო კომპიუტერზე)

ბრაუზერი სკანერს პირდაპირ ვერ მართავს. ამიტომ კომპიუტერზე მუშაობს პატარა აგენტი (`scanner-agent/`). ის უსმენს მხოლოდ `127.0.0.1:7777`-ს, პასუხობს მხოლოდ კონფიგში ჩაწერილ საიტს და სკანირებს უფასო NAPS2-ით (WIA/TWAIN).

**ინსტალაცია (ყოველ კომპიუტერზე):**

1. დააყენეთ [NAPS2](https://www.naps2.com/download) (ნაგულისხმევ საქაღალდეში).
2. გაუშვით **`ClinicScanAgentSetup.exe`** (ადმინის უფლება და Node.js არ სჭირდება) → ჩაწერეთ **საიტის მისამართი** ზუსტად ისე, როგორც ბრაუზერის მისამართის ზოლშია (მაგ. `http://10.1.20.5:3000`; რამდენიმე — მძიმით) → „დაყენება“. ფანჯარა აჩვენებს, ნაპოვნია თუ არა NAPS2.
3. აგენტი ეშვება ახლავე და Windows-ში ყოველ შესვლისას, ფანჯრის გარეშე. ეკრანის ქვედა მარჯვენა კუთხეში — **ხატულა**: მწვანე — მუშაობს, ნარინჯისფერი — NAPS2 ვერ მოიძებნა, წითელი — არ მუშაობს. ხატულის მენიუ: **საიტის მისამართის შეცვლა**, აგენტის გადატვირთვა, ლოგი.
4. საიტზე ⚙ ღილაკით აირჩიეთ სკანერი, გარჩევადობა და წყარო. არჩევანი ინახება ამ კომპიუტერზე. თუ სკანერი არჩეული არ არის, გამოიყენება პირველი ხელმისაწვდომი.

პირველ სკანირებაზე Chrome/Edge შეიძლება ითხოვდეს ნებართვას ლოკალურ ქსელზე წვდომისთვის: დააჭირეთ „Allow“. **წაშლა:** „პარამეტრები → აპლიკაციები → Clinic Scan Agent“. თუ აგენტი მიუწვდომელია, გამოიყენეთ „ფაილის ატვირთვა“. ფაილები: `%LOCALAPPDATA%\ClinicScanAgent` (ლოგი — `agent.log`).

ციფრული ხელმოწერის გარეშე Windows შეიძლება აჩვენებდეს „Windows protected your PC“ — „More info“ → „Run anyway“.

**ინსტალატორის აწყობა** (Windows, Node.js 24): `npm run scanner:build` → `scanner-agent/dist/ClinicScanAgentSetup.exe`. აგენტი (`agent.mjs`) იქცევა ცალკე exe-დ (Node.js Single Executable Application), ინსტალატორი — Windows-ის ჩაშენებული IExpress-ით; ინსტალაციის სკრიპტები — `scanner-agent/installer/`. ფანჯრის გარეშე (ბევრ კომპიუტერზე ერთბაშად): ამოაარქივეთ (`ClinicScanAgentSetup.exe /C /T:<საქაღალდე>`) და `powershell -ExecutionPolicy Bypass -File setup.ps1 -Origin "http://10.1.20.5:3000" -Quiet`.

დეველოპმენტისთვის (Node.js-ით, ინსტალატორის გარეშე): `scanner-agent\install.ps1 -Origin "..."`.

## ახალი მომხმარებლის დამატება სკრიპტით

```bash
npm run user:create -- <username> <password> <სახელი> <გვარი> <როლის_კოდი>
```

მაგალითი:

```bash
npm run user:create -- nino.b "Pass1234!" ნინო ბერიძე doctor
```

როლის კოდები: `admin`, `registrar`, `doctor`, `nurse`, `lab`, `accountant`, `director`.
პაროლი მინიმუმ 8 სიმბოლო; ჰეშირდება bcrypt-ით (cost 12).

მომხმარებლის გასათიშად გამოიყენეთ ადმინისტრატორის პანელი. გათიშულ მომხმარებელს სესია მაშინვე უწყდება.
