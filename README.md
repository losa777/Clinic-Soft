# კლინიკა — მართვის სისტემა

პირველი ეტაპი: ავტორიზაცია და როლების მიხედვით გვერდები.

**ტექნოლოგიები:** Next.js 16 (App Router, TypeScript), Auth.js v5 (Credentials, JWT), Prisma 7 + MariaDB/MySQL, Tailwind CSS 4 + shadcn/ui, zod, bcryptjs.

## მოთხოვნები

- Node.js 20.9+ (ტესტირებულია 24-ზე)
- MariaDB ან MySQL სერვერი და ცარიელი (ან არსებული) ბაზა, მაგ. `clinic`

## ინსტალაცია

```bash
npm install
```

`npm install` ავტომატურად უშვებს `prisma generate`-ს (კლიენტი იქმნება `src/generated/prisma`-ში).

## .env-ის შევსება

დააკოპირეთ `.env.example` → `.env.local` და შეავსეთ:

```env
DB_HOST=10.1.20.242
DB_PORT=3306
DB_USER=...
DB_PASSWORD=...
DB_NAME=clinic
AUTH_SECRET=...
```

`AUTH_SECRET`-ის დასაგენერირებლად:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

> `npx auth secret` ახლა Better Auth-ის CLI-ს უშვებს და სხვა ცვლადს (`BETTER_AUTH_SECRET`) აგენერირებს, ამიტომ გამოიყენეთ ზემოთ მოცემული ბრძანება.

`.env.local` არის `.gitignore`-ში — პაროლები რეპოზიტორიაში არ ხვდება. ბაზის მონაცემები კოდში არსად წერია; მათ კითხულობს `src/lib/db-config.ts`.

## ბაზის მომზადება

```bash
npm run db:setup
```

სკრიპტი (`scripts/setup-db.ts`) იდემპოტენტურია — შეგიძლიათ გაუშვათ რამდენჯერმე:

- ქმნის ცხრილებს `roles`, `users`, `patients` და `patient_documents` (`CREATE TABLE IF NOT EXISTS`, InnoDB, `utf8mb4_unicode_ci`);
- წერს 7 როლს (`INSERT ... ON DUPLICATE KEY UPDATE`);
- ქმნის სატესტო მომხმარებლებს და ბეჭდავს სიას.

განმეორებით გაშვებისას არსებულ მომხმარებელს პაროლი **არ** ეცვლება (განახლდება მხოლოდ სახელი, გვარი და როლი).

ცხრილის სტრუქტურა აღწერილია `prisma/schema.prisma`-შიც (Prisma კლიენტისთვის). სტრუქტურის შეცვლისას განაახლეთ ორივე ფაილი.

## გაშვება

```bash
npm run dev      # დეველოპმენტი: http://localhost:3000
npm run build    # production build
npm start        # production სერვერი (build-ის შემდეგ)
```

production-ში (`npm start`) Auth.js მისამართს ენდობა მხოლოდ თუ `.env.local`-შია `AUTH_TRUST_HOST=true` (ან `AUTH_URL=https://<საიტი>`) — სხვაგვარად შესვლა ვერ ხერხდება (`UntrustedHost`).

## ადმინისტრატორის პანელი

ადმინისტრატორის გვერდზე (`/admin`) არის სამი ჩანართი:

- **მიმოხილვა** (`/admin`): მომხმარებლების და როლების რაოდენობა.
- **მომხმარებლები** (`/admin/users`): ცხრილი ძებნით, ფილტრებით (როლი, სტატუსი), სორტირებით და გვერდებით. აქვე ხდება დამატება, რედაქტირება, პაროლის შეცვლა, გათიშვა/გააქტიურება და წაშლა.
- **როლები** (`/admin/roles`): ახალი როლის დამატება, სახელის შეცვლა, წაშლა, **უფლებების** მინიჭება (იხ. „უფლებები“).
- **პაციენტები** (`/admin/patients`): პაციენტის მონაცემების და დოკუმენტების რედაქტირება.
- **სერვისები** (`/admin/services`): სერვისები კატეგორიებით (დასახელება უნიკალურია, ICD-10 კოდი — არასავალდებულო), ფასი ლარში. დამატება, რედაქტირება, **დეაქტივაცია** (სერვისი აღარ იშლება — ინვოისებშია). ფასის ცვლილება იწერება `service_price_history`-ში და უკვე გაცემულ ინვოისებს არ ცვლის. „კატეგორიები“ — დამატება/გადარქმევა.
- **დაზღვევა** (`/admin/insurance`): სადაზღვევო კომპანიები და პირობები — დაფარვის % და ლიმიტი ერთეულზე, სერვისზე ან მთელ კატეგორიაზე (სერვისის პირობა უპირატესია).
- **რეკვიზიტები** (`/admin/settings`): კლინიკის დასახელება, ს/კ, მისამართი, ტელეფონი, ქვითრის ბოლო ტექსტი (`settings` ცხრილი).
- **ექიმები** (`/admin/doctors`): „ექიმის“ როლის მომხმარებლები. თითოეულს ენიჭება სპეციალობა, ვიზიტის ხანგრძლივობა, კაბინეტი, ჯავშნისთვის ხელმისაწვდომობა და **კვირის სამუშაო განრიგი** (`/admin/doctors/<userId>`). განრიგში თითო დღეს შეიძლება რამდენიმე ინტერვალი ჰქონდეს. ჯავშნის სლოტები ამ განრიგიდან ითვლება. არსებული ჯავშნები განრიგის შეცვლისას არ იცვლება: შენახვის შემდეგ ჩანს, რამდენი მომავალი ჯავშანი აღარ ემთხვევა ახალ განრიგს. ახალი ექიმი ჯერ „მომხმარებლებში“ ემატება `doctor` როლით.
- **სპეციალობები** (`/admin/specialties`): დამატება, გადარქმევა, წაშლა. წაიშლება მხოლოდ ის სპეციალობა, რომელიც არცერთ ექიმს არ აქვს მინიჭებული.

**წესები:**

- ადმინისტრატორი საკუთარ ანგარიშს ვერ წაშლის, ვერ გათიშავს და საკუთარ თავს ადმინის როლს ვერ ჩამოართმევს.
- სისტემაში ერთი აქტიური ადმინისტრატორი მაინც უნდა დარჩეს.
- 7 სისტემური როლი (`src/lib/roles.ts`) არ იშლება, მათი სახელის შეცვლა კი შეიძლება.
- როლი, რომელსაც მომხმარებლები ჰყავს, არ იშლება.
- როლის კოდი შექმნის შემდეგ არ იცვლება, რადგან ის გვერდის მისამართია (`/surgeon`). დამატებითი როლის მომხმარებელი შესვლისას საერთო როლის გვერდს ხედავს.
- გათიშვა, წაშლა და როლის ან სახელის შეცვლა **მაშინვე** მოქმედებს: სესია ყოველ მოთხოვნაზე მოწმდება ბაზაში.
- წაშლა შეუქცევადია. თუ წვდომა მხოლოდ დროებით უნდა შეიზღუდოს, გამოიყენეთ „გათიშვა“.

ყველა Server Action სერვერზე თავიდან ამოწმებს, რომ მომხმარებელი ადმინისტრატორია (`requireRole("admin")`).

## პაციენტის რეგისტრაცია

- **რეგისტრატორი**:
  - `/registrar`: ძებნა სახელით და გვარით (ნებისმიერი რიგით, ქართულად ან ლათინურად) ან პირადი ნომრით (სრულით ან მინიმუმ 4 პირველი ციფრით). შედეგში ჩანს სახელი, გვარი, ტელეფონი, პირადი ნომერი და დაბადების თარიღი; ერთდროულად მაქსიმუმ 20 შედეგი. ძებნა მუშაობს ინდექსებით, სიტყვის დასაწყისით.
  - `/registrar/patients/<id>`: პაციენტის სრული ინფორმაცია მხოლოდ სანახავად, დოკუმენტების დამატება შეიძლება.
  - `/registrar/new`: ახალი პაციენტის რეგისტრაცია. ძებნიდან გადმოსვლისას პირადი ნომერი ან სახელი/გვარი უკვე შევსებულია. შენახვის შემდეგ იხსნება პაციენტის გვერდი.

  - რეგისტრაციისას (აქ და ჯავშნისას სწრაფ ფორმაში) შეიძლება მიეთითოს **დაზღვევა** — „პაციენტი დაზღვეულია“: კომპანია, პოლისის ნომერი, ვადა. არასავალდებულოა; პაციენტი და პოლისი ერთ ტრანზაქციაში ინახება (უფლება: `invoices.create` ან `insurance.manage`).
  - პაციენტის ბარათს აქვს ჩანართები: **„ინვოისები“** (ჯამური ვალი, ინვოისების სია, „ახალი ინვოისი“) და **„დაზღვევა“** (პოლისები: დამატება, გათიშვა). ძებნის შედეგებში ვალიანი პაციენტი „ვალი: …“ ნიშნით ჩანს. ინვოისები და გადახდები: იხ. „ფინანსები“.
- **ადმინისტრატორს** `/admin/patients`-ში აქვს ძებნა, პაციენტის ბარათი მონაცემების რედაქტირებით, ინვოისების სია (სანახავად) და პოლისები. ახალი პაციენტის რეგისტრაცია მხოლოდ რეგისტრატორს აქვს (სერვერზეც მოწმდება).

  არსებული პაციენტის მონაცემებს რეგისტრატორი ვერ ცვლის.
- **ადმინისტრატორი** (`/admin/patients`): იგივე ფორმა, დამატებით არსებული პაციენტის რედაქტირება და დოკუმენტის წაშლა.

ძებნა იწყება 11-ე ციფრის შეყვანისას ან ველიდან გასვლისას (`patients.personal_id`-ის UNIQUE ინდექსით). ნომრის შეცვლისას ნაპოვნი პაციენტის მონაცემები ფორმიდან იშლება. First Name / Last Name ავტომატურად ივსება ქართულიდან (`src/lib/transliterate.ts`), სანამ ხელით არ შეცვლით.

**დოკუმენტები** ინახება დისკზე, `DOCUMENTS_DIR` საქაღალდეში (`.env.local`). ის უნდა იყოს პროექტის და `public/`-ის გარეთ, და მისი სარეზერვო ასლი უნდა კეთდებოდეს ბაზასთან ერთად. ბაზაში (`patient_documents`) მხოლოდ მეტამონაცემებია. ფაილი იკითხება მხოლოდ `/api/patient-documents/<id>`-ით, სესიისა და როლის შემოწმების შემდეგ. დასაშვებია JPG, PNG და PDF; ტიპი მოწმდება ფაილის შიგთავსით. ლიმიტია 10 MB ფაილზე და 10 ფაილი / 40 MB ერთ შენახვაზე. დასკანერებული ფაილები შენახვამდე ბრაუზერშია; შენახვისას ჯერ იწერება დისკზე, მერე პაციენტი და დოკუმენტები ერთ ტრანზაქციაში. ჩავარდნისას ჩაწერილი ფაილები იშლება.

ტესტები: `npm test` (Node-ის ჩაშენებული test runner).

## ექიმთან ვიზიტის დაჯავშნა

ცხრილები: `specialties`, `doctors` (`users`-ის პროფილი: სპეციალობა, ვიზიტის ხანგრძლივობა, კაბინეტი, აქტიურობა), `doctor_schedules` (კვირის დღე 1–7, დრო თბილისის დროით; დღეში რამდენიმე ინტერვალი შეიძლება), `appointments`. იქმნება `npm run db:setup`-ით. სპეციალობებს, ექიმებსა და განრიგს მართავს ადმინისტრატორი (`/admin/specialties`, `/admin/doctors`). ჯავშნებში ჩანს მხოლოდ ექიმი, რომელიც ხელმისაწვდომადაა მონიშნული, მომხმარებელი აქტიურია და აქვს `doctor` როლი. სატესტო მონაცემები (5 სპეციალობა, 6 ექიმი გრაფიკით, 20 პაციენტი, პირადი ნომრები `01099000001`–`01099000020`) ემატება ბრძანებით:


## ფინანსები (`src/modules/finance/`)

ძველი „პაციენტის მიღება“ (`visits`, `visit_services`, `visit_payments`) ჩაანაცვლა ინვოისებმა: `db:setup` ძველ ვიზიტებს ერთხელ გადაიტანს ინვოისებში (`legacy_visit_id`), ძველი ცხრილები არქივად რჩება.

**რეგისტრატურა:** ჩანართები „ინვოისები“, „სალარო“, „დავალიანებები“, „ანგარიშები“. **ბუღალტერი/დირექტორი** (`/accountant`, `/director`): დღის ანგარიში, ინვოისები და დავალიანებები — მხოლოდ სანახავად.

- **ინვოისი** (`INV-2026-000001`, წლის მიხედვით თანმიმდევრული): იქმნება პაციენტის ბარათიდან, ძებნის შედეგიდან ან ჯავშნიდან („ჯავშნები“ → „ინვოისი“ — ექიმი და ექიმის **კონსულტაციის სერვისი** ჩაჯდება ავტომატურად; კონსულტაციის სერვისი ექიმს ენიჭება „ადმინი → ექიმები“). სერვისები ძებნით, რაოდენობა, ფასდაკლება %. ერთ ჯავშანზე ერთი ინვოისი.
- **დაზღვევა**: პაციენტის მოქმედი პოლისით (აქტიური, თარიღებში, კომპანია აქტიური) ყოველ ხაზზე ითვლება დაზღვევის წილი = (ფასი × რაოდ. − ფასდაკლება) × % , მაგრამ არა მეტი ლიმიტი × რაოდ.; დანარჩენი — პაციენტის თანაგადახდა. დაზღვევა კონკრეტულ ინვოისზე შეიძლება გამოირთოს მიზეზით.
- **გადახდა**: ნაღდი (მხოლოდ ღია ცვლით; მიღებული თანხა → ხურდა) ან ბარათი (ტრანზაქციის ნომერი / ბოლო 4 ციფრი — სრული ნომერი არ მიიღება). შეიძლება ნაწილობრივი და რამდენიმე გადახდა; ზედმეტი გადახდა არ მიიღება. **დაბრუნება** (`payments.refund`) — ახალი ჩანაწერი მიზეზით. **გაუქმება** — მიზეზით, მხოლოდ თუ გადახდილი თანხა არ არის (ჯერ დაბრუნება).
- **ქვითარი** ყოველ გადახდასა და დაბრუნებაზე (`RCP-2026-000001`): 80 მმ თერმო ან A4, რეკვიზიტებით; ყოველი ბეჭდვა აღირიცხება, პირველის შემდეგ — „დუბლიკატი“.
- **დავალიანება** = გადაუხდელი პაციენტის წილი ღია ინვოისებზე — ყოველთვის ითვლება მოთხოვნით (ცალკე ველი არ არის). სია ფილტრით (ინვოისის თარიღი, მინ. თანხა), გვერდებით, CSV ექსპორტით (Excel ხსნის); სადაზღვევო დავალიანება კომპანიების მიხედვით პერიოდში.
- **სალარო**: ცვლის გახსნა საწყისი ნაღდით (ერთ მომხმარებელს ერთი ღია ცვლა — ბაზის UNIQUE); დახურვისას მოსალოდნელი = საწყისი + ნაღდი გადახდები − ნაღდი დაბრუნებები, ფაქტობრივი შეყავს მოლარეს, სხვაობა ინახება (სხვაობისას განმარტება სავალდებულოა).
- **დღის ანგარიში** (თარიღი, მოლარე): ნაღდი, ბარათი, დაბრუნებები, ინვოისები და დაზღვევის წილი, სერვისების მიხედვით, გაუქმებული ინვოისები და დაბრუნებები; ბეჭდვა და CSV.

**წესები:** თანხები DECIMAL(12,2), გამოთვლა სერვერზე მთელ თეთრებში (`src/modules/finance/calc.ts`, ტესტები — `calc.test.mts`). გადახდა, დაბრუნება, ქვითარი არ იცვლება და არ იშლება. ყველა ოპერაციაში ინახება ვინ და როდის. მრავალნაბიჯიანი ოპერაციები ერთ ტრანზაქციაშია: ინვოისი/ცვლა იკეტება (`SELECT … FOR UPDATE`), ამიტომ ერთდროული გადახდები ზედმეტს ვერ ჩაწერს. ანგარიშები და ვალი SQL-ში აგრეგაციით ითვლება.

**სტრუქტურა:** `calc.ts` (სუფთა გამოთვლები), `schema.ts` (zod), `server/` (ფასი/დაზღვევა, ინვოისები, გადახდები, სალარო, ვალი, ანგარიშები), `actions/` (Server Actions, `requirePermission`), `components/` (InvoiceForm, PaymentForm, ReceiptPrint, DebtList, CashShiftPanel, DailyReport…), `screens/` (როლზე დამოუკიდებელი გვერდები), `routes.ts` (მისამართები როლების მიხედვით — ახალი როლისთვის ჩანაწერი აქ და გვერდები, ნიმუშია `accountant/`).

## სკანერი (სარეგისტრატურო კომპიუტერზე)

ბრაუზერი სკანერს პირდაპირ ვერ მართავს. ამიტომ კომპიუტერზე მუშაობს პატარა აგენტი (`scanner-agent/`). ის უსმენს მხოლოდ `127.0.0.1:7777`-ს, პასუხობს მხოლოდ კონფიგში ჩაწერილ საიტს და სკანირებს უფასო NAPS2-ით (WIA/TWAIN).

1. დააყენეთ [NAPS2](https://www.naps2.com) (ნაგულისხმევ საქაღალდეში) და [Node.js](https://nodejs.org) 20+.
2. დააკოპირეთ `scanner-agent` საქაღალდე კომპიუტერზე და მასში გაუშვით (ადმინის უფლება არ სჭირდება):
   ```powershell
   powershell -ExecutionPolicy Bypass -File .\install.ps1 -Origin "https://<კლინიკის-საიტი>"
   ```
   `-Origin` ზუსტად ის მისამართია, რომელიც ბრაუზერის მისამართის ზოლშია (პორტით, ბოლო `/` გარეშე). რამდენიმე მისამართი მძიმით ჩამოწერეთ.
3. აგენტი ეშვება ახლავე და ყოველ შესვლისას ავტომატურად (Startup), ფანჯრის გარეშე. ლოგი: `%LOCALAPPDATA%\ClinicScanAgent\agent.log`.
4. საიტზე ⚙ ღილაკით აირჩიეთ სკანერი, გარჩევადობა და წყარო. არჩევანი ინახება ამ კომპიუტერზე. თუ სკანერი არჩეული არ არის, გამოიყენება პირველი ხელმისაწვდომი.

პირველ სკანირებაზე Chrome/Edge შეიძლება ითხოვდეს ნებართვას ლოკალურ ქსელზე წვდომისთვის: დააჭირეთ „Allow“. წაშლა: `uninstall.ps1`. თუ აგენტი მიუწვდომელია, გამოიყენეთ „ფაილის ატვირთვა“.

**წესები:**

- შეუსვლელი მომხმარებელი ნებისმიერი გვერდიდან → `/login`
- შესული მომხმარებელი `/login`-ზე ან `/`-ზე → თავისი როლის გვერდზე
- სხვა როლის გვერდზე შესვლის მცდელობა (მაგ. ექთანი → `/director`) → თავის გვერდზე

ეს შემოწმება ხდება ორჯერ: `proxy.ts`-ში და სერვერზე, layout-ში და გვერდზე (`src/lib/dal.ts`).

როლისთვის საკუთარი გვერდების დასამატებლად შექმენით საქაღალდე `src/app/(dashboard)/<კოდი>/`. მაგალითად, `doctor/` გადაფარავს საერთო `[role]` გვერდს. მის layout-ში გამოიძახეთ `requireRole("<კოდი>")` (ნიმუშია `admin/layout.tsx`).
